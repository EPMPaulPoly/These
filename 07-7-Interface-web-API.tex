\section{Outil de gestion proposé}\label{sec:meth_tool}
La section \ref{sec:meth_urb_based_inventory} a décrit la méthode utilisée pour entreposer les informations réglementaires et calculer une estimation à partir de ces informations. Cependant, la création de cette réglementation est onéreuse et peu intuitive. Cette section visera à proposer un outil qui permet de générer la réglementation, d'en extraire l'information pertinente, et de permettre à des praticiens d'accéder aux estimations de capacités pour d'autres études. La section  commence par discuter des requis informels mis en place en début de projet avant de montrer comment l'outil est implémenté.
Les détails d'implémentation sont discutés dans la section des résultats d'outils à la section \ref{sec:outil_develope}.
\subsection{Requis}

\paragraph{Interface avec la base de données et cohérence des données}

En premier lieu, il doit être possible de créer, modifier et supprimer des données sur la base de données tout en assurant la cohérence des données. Idéalement, il serait possible d'automatiser des fonctionnalités de validation de la base de données pour trouver de potentielles erreurs dans les données fournies.

\paragraph{Calcul réglementaire basé sur les données foncières}

L'interface doit permettre la création d'une estimation à partir des données du rôle foncier au moyen  de l'algorithme détaillé dans la section \ref{sec:meth_urb_based_inventory}. Il devrait ensuite être possible de valider les estimations contre un échantillon d'évaluation.

\paragraph{Calcul réglementaire avec entrée manuelle}

Environ 30 à 35\% des lots commerciaux et de service dans le rôle foncier n'ont pas de superficies listées. L'implémentation d'une méthode semi-automatique est un outil qui permet de pallier cet enjeu en partie. Si une conversion est mal implémentée, cette fonctionnalité permet aussi de rapidement modifier le résultat tout en gardant la prédiction automatique stockée.

\paragraph{Entrée manuelle d'une capacité de stationnement}

L'outil doit permettre la saisie d'un comptage manuel sur un lot.

\paragraph{Comparaison des ensembles de règlements} 

L'outil doit permettre de faire une comparaison graphique entre différents ensembles de règlements pour différentes utilisations du sol en fonction du temps et de la géographie.
\paragraph{Visualisation de l'estimation du nombre de places sur un territoire}

L'outil devra permettre une représentation graphique de l’estimation à différents niveaux d'agrégation (quartier, territoire complet).
\paragraph{Capacité de créer un échantillon de validation}

L'outil doit permettre de créer des échantillons de lots selon des critères définis par l'utilisateur pour évaluer la précision du modèle.

\paragraph{Accessibilité à partir de tierces parties} 

Une partie ou l'ensemble des données devra être accessible à partir d'autres scripts au moyen d'une API. Le but sera ici d'assurer que les données générées puissent être utilisées pour comprendre l'effet de l'offre de stationnement sur les comportements de mobilité dans le contexte québécois.

\subsection{Architecture de l'outil proposé}

Différentes solutions peuvent être envisagées pour gérer des données spécialisées. Une estimation de la capacité de stationnement pourrait être générée et interprétée dans différents logiciels (SIG, tableurs), mais cela rend la création, le maintien et l'interprétation et la visualisation des estimations complexes, particulièrement si plusieurs estimations doivent co-habiter. Alternativement, un outil spécialisé peut être créé. Cette approche a été privilégiée principalement parce que l'auteur avait de la difficulté à s'y retrouver en devant se référer uniquement à des tables. Différentes implémentations sont cependant possibles.\par

Ce dernier peut être un logiciel installé sur les ordinateurs personnels de différents analystes ou une application web avec une infrastructure centralisée pour faire les calculs et publier l'information, ou une solution hybride avec une infrastructure centralisée qui est utilisée pour la sauvegarde des données avec un outil local pour manipuler les valeurs. \par

La solution entièrement en ligne a été retenue pour plusieurs raisons. Premièrement, cela évite la duplication d'information et permettrait à un organisme de maintenir l'inventaire et de le rendre disponible à d'autres parties prenantes pour faire des analyses. D'autre part, cela permet de centraliser les ressources de calcul et de mettre à jour l'outil au besoin sans avoir à assurer le support de différentes versions. Ce type d'implémentation serait aussi compatible avec l'utilisation des données par d'autres logiciels. Ces derniers feront alors appel à l'\ac{API}. Ce type d'arrangement est typique dans les applications web \parencite{chernenko_full_2024}. Dans ce cas, un morceau de code TypeScript est téléchargé sur la machine \og{client} \fg{} à partir du serveur. Cet ensemble de procédures informatiques fait le rendu de la page web. Les informations et les données sont demandées par le script \og{client} \fg{} au serveur de données qui renvoie les données pertinentes à la requête.\par

L'\ac{API} est un format de requête utilisée entre le script \og{client}\fg{} qui fonctionne sur le fureteur et les scripts \og{serveur}\fg{} qui interagissent avec la base de données. L'implémentation proposée reprend librement le standard \ac{REST} \parencite{fielding_architectural_2000} qui transmet les requêtes et les réponses au moyen du protocole \ac{HTTP}. Ce type d'interface a typiquement 4 grandes fonctions: GET, PUT, POST, DELETE. GET sert à obtenir un élément de la base de données. PUT permet de modifier un élément déjà existant. POST permet de créer un nouvel élément dans une table. DELETE sert à supprimer un élément. Le chemin (\ac{URI}) auquel ces instructions sont transmises détermine quelle table dans la base de données est consultée ou modifiée. Une liste complète des variations de GET/PUT/POST/DELETE, d'\ac{URI} et de paramètres est dressée à l'annexe \ref{ann:api-routes}. Une synthèse visuelle de l'\ac{API} est dressée à la section \ref{sec:api-functions}.\par 

D'autre part, de l'information peut être envoyée dans l'\ac{URI} ou dans le corps du message. Dans le cas de l'\ac{URI}, un identifiant peut être communiqué dans l'adresse directement qui peut être ainsi lu. Ceci est souvent le cas quand on connait l'identifiant unique de l'élément à obtenir. L'autre option pour l'URL consiste à communiquer l'information au moyen de requête de filtrage (\og{query parameters} \fg{} en anglais). Ces derniers sont implémentés en insérant un point d'interrogation dans l'\ac{URI} , puis en séparant les paramètres de recherche par des \&. Ce type d'implémentation est souvent mis en place si l'identifiant n'est pas disponible. Dans le cadre de ce mémoire, ce type d'implémentation est principalement mis en place pour la recherche de règlement. Ainsi, un appel d'\ac{API} pour des règlements dont la date de début est après 2008 serait un appel GET à l'adresse \og{/api/reglements/entetes?annee\_debut\_après=2008}\fg{}. Dans le cas de figure où l'on connait l'identifiant, par exemple si l'on veut voir les détails d'un règlement à la requête de l'utilisateur, on pourrait faire l'appel GET à l'adresse \og{/api/reglements/complet/<id>} \fg où l'identifiant est directement spécifié dans l'adresse sans chaîne de caractère supplémentaire. L'information peut aussi être contenue dans le corps du message plutôt que dans l'adresse. Ce type de fonctionnalité est principalement utilisé pour les cas de figure où l'on veut modifier ou créer un élément dans la base de données.\par

Le code principal est structuré dans un dépôt GitHub \parencite{charbonneau_epmpaulpolyinterface_backend_stationnement_maitrise_2025}. La structure du dossier est donnée à la figure \ref{fig:project-directory-structure}. Le dépôt est structuré à l'aide de trois grands dossiers: \og{client}\fg{}  où les fichiers envoyés au fureteur sont entreposés, \og{serveur}\fg{} où sont entreposés les scripts TypeScript qui gèrent la plupart des requêtes de données et \og{serveur\_calcul\_python}\fg{} qui contient des scripts Python qui gèrent les requêtes plus complexes. Le dossier \og{client} \fg{} contient les scripts qui gèrent le rendu de l'application sur le fureteur de l'utilisateur. Le fichier \og{index.html}\fg{} est le point d'entrée du site web qui navigue via \og{index.tsx}\fg{} et \og{App.tsx}\fg{} aux 10 pages implémentées dans le dossier \og{pages}\fg{}. Ces pages sont constituées de composantes qui se trouvent dans le dossier \og{components}\fg{}. Les composantes ou les pages utilisent les scripts situés dans le dossier \og{service}\fg{} pour faire des requêtes au moyen du protocole formalisé par l'\ac{API} au serveur qui lui fait l'interaction avec la base de données. Les types sont définis dans le dossier du même nom. Finalement, le dossier \og{utils}\fg{} contient des utilitaires qui sont utilisés par plusieurs pages ou requièrent des manipulations plus complexes et sont implémentés séparément. Les fichiers \og{package.json}\fg{} et \og{tsconfig.json}\fg{} sont des fichiers de configuration. Le premier définit les librairies externes à installer tandis que le deuxième fixe la configuration TypeScript. \par


Les fonctionnalités exécutées sur le serveur sont implémentées dans deux dossiers. Le premier est nommé \og{serveur}\fg{} et sert de point d'entrée  pour les requêtes formulées selon le standard défini par l'\ac{API}.  Les requêtes faites au serveur sont acheminées via le script \og{serveur.ts}\fg{} à \og{index.ts}\fg{} dans le dossier \og{api}\fg{}. \og{index.ts}\fg{} achemine ensuite les requêtes aux 12 scripts (\og{historique.ts}\fg{}, \og{Inventaire.ts}\fg{}, etc.)  qui gèrent chacun les opérations pour un grand type de donnée. Les scripts exécutent des requêtes SQL et formatent les données pour les renvoyer au client. Encore une fois, des fichiers \og{package.json}\fg{}, \og{tsconfig.json}\fg{} configurent les librairies et Typescript. \og{nodemon.json}\fg{} quant à lui configure des fonctions pour permettre le débogage.\par 

Lorsqu'une opération ne peut être faite par une simple requête SQL, les 12 scripts peuvent lancer un des 9 scripts Python dans la racine du dossier \og{serveur\_calcul\_python}\fg{}. Ils appellent des fonctions et méthodes implémentées dans le dossier \og{classes}\fg{}. Les classes se situent dans le dossier \og{classes}\fg{} et suivent le schéma mis de l'avant dans la section \ref{ssec:obj-informatique-impl-stat}. Le fichier \og{environnement.yml}\fg{} contient la liste des librairies Python à installer pour faire fonctionner les méthodes et fonctions contenues dans le dossier.\par

Le code est implémenté pour utiliser des conteneurs \og{Docker}\fg{}. \og{Docker}\fg{} est une machine virtuelle. Ceci permet de garantir un environnement stable et la réplication relativement simple sur un serveur tiers. La base de données est implémentée directement sur l'ordinateur de l'utilisateur. Cette approche a été prise pour assurer la persistance de la base de données en cas de corruption de l'instance \og{Docker}\fg{}. Trois fichiers de configuration sont utilisés pour configurer le système. Le premier, \og{docker-compose.yml}\fg,{} crée les conteneurs \og{Docker}\fg{}, définit leur structure, les fichiers \og{DockerFile}\fg{} à utiliser et les variables d'environnement pour le conteneur. Les deux fichiers \og{DockerFile}\fg{} sont une liste de commandes à exécuter au démarrage de l'instance. Ces commandes installent les différentes librairies et logiciels dans chacun des conteneurs. \par
